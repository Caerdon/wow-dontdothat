# Rule data schema

Rule data files live in `DontDoThat/Rules/Data/` and call `ns.Rules.Load(table)`. `Load` validates the table and raises a message beginning `DontDoThat rule data (<id>): ...` on malformed data. Money is integer copper. Anything unverified is commented in the data file.

## Spell names and IDs

Rule files are written with English spell names (the Classic Era names, which the Forever tables sometimes rename: Curse of Agony is Bane of Agony). `ns.Rules.Load` compiles every name to a spell family ID (`SpellData.FamilyId`, see `docs/contracts.md`), and the engine, the settings and the Rules page work in IDs only. Anywhere the table below says "name" it means this.

- A name that matches no spell raises `DontDoThat rule data (<class> <field>): no spell named '<name>' for this class`, and `tests/spell_ids_test.lua` fails on it.
- A key or list entry written `~Prefix` stands for every family whose name starts with the prefix (`~Create Firestone` covers Lesser, normal, Greater and Major). It must match at least one.
- Professions (`ProfessionLearn.lua`) are identified by the spell ID of their apprentice tier, for example Cooking = 2550. `gathering` lists the ones that are never asked about and must also appear in `apprentice`.
- The trainer-based tables (`Data/SpellData.lua`) do not list talent-granted spells, default attacks or conjured items. Add such a name to `tools/rule-spell-names.txt` (`CLASS<TAB>Name`) and run `python3 -I tools/build-rule-spells.py` to write `Data/RuleSpells.lua`. It looks the name up in the Classic Era and Forever tables, so it needs the cached wago CSVs in `tools/.cache`.
- The Warlock `grimoires.keep` list names demon abilities, not items. A grimoire is recognised by its item ID (the number in its item link), and `Data/RuleItems.lua` maps each grimoire item ID to its ability. Regenerate it with `python3 -I tools/build-rule-items.py`, which downloads the item tables into `tools/.cache/items`. `tests/grimoires_test.lua` fails on a kept name that no grimoire has.

## Class data (`class = "HUNTER"`)

| Field | Meaning |
|---|---|
| `specs[KEY]` | `{ name, rotation = { core = {names}, situational = {names}, needsReview = bool } }`. `needsReview` marks thinly sourced rotations; the Rules page must label them. |
| `tagTiers` | Tag to default tier, e.g. `PvP = "deferLow"`, `RaidGroup = "defer"`. Tiers: `keep`, `info`, `deferLow`, `defer`. |
| `tags` | Ability name to list of tags. Every tag must exist in `tagTiers`. The most severe tier wins. |
| `overrides` | Ability name to tier. Beats everything else. |
| `ranks[family]` | List of rows `{ rank, unlockLevel, cost = copper|nil, manaCost = n|nil }`, ranks consecutive from 1, `unlockLevel` non-decreasing. `cost` nil means unknown; a non-nil data cost is reported as an estimate. |
| `abilityLevels` | Optional ability name to trainer level (informational). |
| `skipRevisions` | Not used by the class files: ranks to skip live in `Data/SkipRevisions.lua` (see Skip revisions below). Synthetic data in tests may carry it, with spell names as keys. |

## Evaluation order

Rules apply only while `profile.milestone.state == "active"`. Then: skipped rank (from the skip revision in use), override, rotation (core in any plausible spec keeps; situational is `info`), tags, ability that belongs only to a non-plausible spec (`deferLow`, reason names the spec and tree split), keep. Empty or missing `plausibleSpecs` means every spec is plausible.

## Skip revisions

Which spell ranks to skip is not in the class files. `Data/SkipRevisions.lua` (generated by `tools/build-skip-revisions.py`, never edited by hand) holds numbered revisions per class:

```
ns.SkipRevisions[CLASS][revision] = { inherits = <earlier revision> | nil,
  entries = { [familyId] = { [rank] = { entry, ... } } } }
entry = { source = "guide" | "computed" | "legacy", reason = { kind = "...", n | pct = <number> }, specs = { "ARMS", "FURY" } | nil }
```

- Keys are numbers: the spell family ID (see `docs/contracts.md`, Spell identity) and the rank number. Rank 1 is never listed, so a spell's first rank is never skipped.
- `specs` nil means every spec of the class. A rank is skipped for a player only when every spec still plausible for them is in the entries' specs.
- `inherits` makes a revision list only what changes. A rank named in a later revision replaces the earlier entry; an empty list for a rank means "not skipped in this revision", whatever an earlier one said.
- Revision 1 is the list as it was before revisions existed (frozen in `tools/skip-revision/revision1.json`). Revision 2 inherits it. The newest revision is the default; the player picks an earlier one with `/ddt revision n` or on the Tuning page.
- `source` says where the decision came from. `reason.kind` is one of `guideFirstRankOnly`, `guideSkipEntirely`, `guideUpToRank` (n), `guideNotTrained`, `noGain`, `smallStep` (pct), `notWorthPrice` (pct), `waitForMount`, `legacy`. The sentences are in the engine, built from locale text with the numbers filled in, so a reason can be translated and never claims a cause the data does not record.
- Every skip ends when the milestone ends (the level 60 mount bought, or the level 40 mount with "stop after 40"), because rules apply only while the milestone is active. That is how a level 60 rank "waits for the mount".
- `tests/skip_revisions_test.lua` pins revision 1 and checks the shape of revision 2. `tools/skip-revision/README.md` says how revision 2 is built and what it assumes.

## Load order

`Data/SkipRevisions.lua` (it only needs `ns`), `Rules/Schema.lua`, `Rules/Engine.lua`, then the class data files. `Rules.Load` validates a class's revisions against its specs and spell families and flattens `inherits`.
